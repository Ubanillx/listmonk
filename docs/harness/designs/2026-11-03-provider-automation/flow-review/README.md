## 产品理解与任务

这是邮件发件服务的客户自动拉黑工作台。运营者可能需要按投递失败类型和回查天数，分别处理私域或公海客户，并从执行记录核对影响范围。我选择的主任务是：查看私域手动处理条件，理解执行前的核对方式，再从已有条件检查记录核对结果。

**结果：部分完成。** 已到达既有条件检查的明细结果；未发起本次条件检查或拉黑。两个定时开关始终为关闭，未点击开关、保存或“开始拉黑”，未提交任何客户变更。当前浏览器已有个人空间会话，因此本次没有重新登录。没有使用 fixture；下述明细全是既有记录，不是本次真实客户执行。

1. 进入自动拉黑页：看到私域、公海两个范围、均关闭的定时开关和执行记录，于是选择私域的“手动处理”。展开后看到失败类型、回查天数 7、排除邮箱和“开始拉黑”，没有独立的“条件检查”动作。[桌面入口](desktop-overview.png)、[桌面设置](desktop-manual-settings.png)、[手机设置](mobile-manual-settings.png)。
2. 收起设置，打开第一条私域“条件检查”的“查看明细”：列表结果是“待拉黑客户 0”；弹窗加载后显示共 676 条，当前页记录的处理结果是“未匹配邮箱”。这只是对既有记录的只读核对。[桌面明细](desktop-existing-detail.png)、[手机明细](mobile-existing-detail.png)。
3. 自主风险检查：关闭明细，切换执行记录的客户范围到“公海客户”，得到“暂无处理记录”；再切回全部范围，原私域记录出现。移动端再次查看明细并关闭，回到同一记录区域。[公海空状态](desktop-public-empty.png)、[手机入口和记录](mobile-overview.png)。
4. 展开“使用说明”：文字说明手动处理是选择条件后点击“开始拉黑”，核对人数并确认。没有继续点击该动作，因为该入口同时承载可能导致实际客户变更的后续路径，且本次未建立写接口 fixture。

## 关键障碍

### 1. 预检入口以“开始拉黑”呈现，执行边界需要猜测

- **观察事实：** 私域设置区唯一的主动作是“开始拉黑”；页面上没有单独的“条件检查”按钮。折叠在页面末尾的使用说明才说点击后可以核对人数并确认。进入这一步之前，按钮文案没有表达它先是预检、后是不可逆操作。[桌面设置](desktop-manual-settings.png)、[手机设置](mobile-manual-settings.png)。本次停在按钮前，未验证点击后的真实行为。
- **原因推断：** 预检和提交被同一个高风险动词包住，会让谨慎的操作者犹豫，也可能让另一类操作者误以为点击即执行。
- **建议达到的结果：** 在按钮附近明确第一步是只读条件检查，并把“确认拉黑”留到核对人数及范围的下一步；让用户不必先点击危险措辞才能知道影响规模。

### 2. 记录摘要的“0”隐藏了大量未匹配明细

- **观察事实：** 第一条既有私域条件检查在列表中只呈现“待拉黑客户 0”，打开后却显示共 676 条明细，当前页的结果为“未匹配邮箱”。两个数字并不必然矛盾，但必须进入弹窗才看得出 0 指可拉黑人数、676 指检查记录数。[桌面入口](desktop-overview.png)、[桌面明细](desktop-existing-detail.png)。
- **原因推断：** 摘要只强调最终待处理数，缺少未匹配或跳过的分布，容易把“没有可处理客户”理解成“没有命中任何失败记录”。
- **建议达到的结果：** 在记录摘要或明细顶部同时区分检查记录数、匹配客户数、待拉黑数与未匹配/跳过数，保持这组数在跨屏查看时可对照。
