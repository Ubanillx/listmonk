- 技术债清理批次 8：回信转发的失败重试（2026-09-10）。由子代理实施、由本机独立复跑验收。原实现把去重插入写成 `ON CONFLICT DO NOTHING ... RETURNING id`：首次发送失败后行被置为 `failed`，下一轮同 key 命中既有行、`RETURNING` 无结果即 `return nil`，且全仓没有任何消费者读 `failed`/陈旧 `pending` 行——队列拥塞、SMTP 瞬时故障或 reload 会让客户回复**永久不转发**，只在数据库留痕。现把去重门改为原子 **claim**：单条 `INSERT ... ON CONFLICT (rule_id, message_key) DO UPDATE SET status='pending', attempts=attempts+1 ... WHERE (status='failed' AND attempts < 上限 AND 退避已过) OR (status='pending' AND 领取已过期租约) RETURNING id, attempts`，无返回即跳过（已转发／仍有在途领取／已耗尽）。选择「把扫描本身作为重试器」而非独立 worker：原始邮件正文不落库，独立 worker 必须为每条规则重开 POP3 并重新枚举邮箱才能按 key 找回正文，等于复制一遍扫描；而扫描本就每 60 秒重读每个源邮件（源邮件从不删除）。策略：最多 5 次尝试，退避 1m→16m 指数增长，领取租约 5m；耗尽后停在 `failed` + attempts 达上限 + `last_error`，配有结束日志。**无需迁移**：`status`/`attempts`/`last_error`/`updated_at` 均已存在（v6.15.0），在途 = `pending` + 新鲜 `updated_at`，终态 = `failed` + attempts 达上限；旧数据也能恢复（旧 `failed` 行在退避后重试、旧崩溃遗留的 `pending` 在租约后接管、`forwarded` 永不重领）。防重发顺序：①先提交 claim 再发送，并发扫描在行锁上重判 `DO UPDATE ...
