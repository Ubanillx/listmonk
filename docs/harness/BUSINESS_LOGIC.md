# 业务逻辑

## 核心对象

- **工作区**：个人工作区或组织工作区；请求必须先解析并验证当前用户的成员资格和组织状态。
- **客户列表与客户**：客户列表承载客户集合；客户列表和客户默认归属创建者，组织经理可以在当前组织检查成员资源，但不能代替所有者修改或发送。客户列表查询及客户新建、编辑、导入、批量操作和活动受众选择器按当前工作区显示普通列表；客户新建/编辑/普通导入进一步只允许当前操作者拥有的列表，一级公海仍由独立授权路径处理。直接导出仍由 `customers:export` 控制并保持工作区、所有权和打码边界。
- **模板与活动**：模板和活动支持 `private`、`organization`、`global` 可见性；可见不等于可使用、修改或发送。
- **媒体与逻辑文件夹**：媒体二进制仍由 provider 平铺保存；`media_folders` 只保存工作区目录树，`media.folder_id = NULL` 表示根目录。个人目录属于创建者，组织目录属于组织成员可见；目录改名/移动/删除需要 `media:manage`，媒体归属移动还必须由媒体所有者通过 `manage` 检查，空目录才允许删除。活动工作区中的平台管理员媒体页也只展示当前选中工作区，跨工作区资源不能通过拖放改变目录归属；归档工作区只保留平台清理读取能力。
- **用户与角色**：系统用户角色、客户列表角色、组织成员/经理角色和个人 API Key 是独立边界，权限只能收窄，不能扩大资源所有权。
- **一级公海与公海分配**：一级公海保存全局联系人主数据；公海分配只保存一级联系人到组织的分配关系，不复制邮箱。每个“一级公海 × 组织”只允许一个已绑定公海分配，公海分配的手动移除、回复退订和投诉均产生组织维度的逻辑剔除状态，并在一级公海中可见该组织的剔除标记。一级公海与公海分配的联系人在“客户”视图中随所选列表就地展示（仍是独立存储与安全 DTO，不伪装成普通客户），不再有单独的查看页面。
- **公海统一导入**：客户导入入口按所选列表类型分流；普通列表使用客户字段，单个一级 `pool` 列表使用模板字段 `客户编号/客户编码`、`姓名`、`邮箱`、`分配部门`，`分配部门` 必须匹配启用中的 `organizations.name`，未知或已归档部门的行记为无效且不写入，其他模板列忽略。该分支只允许最高管理员操作；公海管理页不再承担导入。
- **公海回件邮箱**：回件邮箱配置在公海分配上，由组织工作区管理员维护。一级公海没有可供组织继承的明文回件邮箱；组织选择一级公海投放时，最终回件邮箱必须由目标组织的二级分配解析。

## 业务审计日志

- `audit_events` 只记录低频业务操作和自动化生命周期，不替代打开、点击、收件人状态或退信事实表。稳定动作名使用英文点号命名，例如 `campaign.status_changed`、`customer.import_started`、`reply.forward_failed`、`audit.exported`。
- 每条记录必须绑定当前工作区（个人空间用 `organization_id = 0`；组织历史保留组织 ID，即使组织删除也不转成个人记录）、操作者类型、结果和对象；浏览器用户/API Key 需要保留用户与 Key ID，后台处理使用 `system`，外部退信使用 `webhook`。查询接口只能读取当前工作区。
- 审计元数据只允许稳定 ID、状态、原因码、数量和诊断摘要；低频对象可附带截断后的 `object_details` 名称/文件名/主题/状态快照，认证操作者可附带 `actor_details` 的名称/用户名。查询在 `actor_user_id` 仍存在时关联用户表展示当前用户名/名称；登录成功在会话建立前绑定用户，失败登录只保存尝试的用户名，媒体移动保存文件名及源/目标目录摘要。不得写入密码、API Key 原文、SMTP 凭据、邮件正文、附件、客户完整收件人集合或可恢复的隐私导出内容。错误原因写固定 reason code，详细错误留在运行日志。
- 活动发送器记录启动、启动失败、完成、暂停、取消和延迟；`campaign_recipients.status = sent` 的含义仍是消息交给 messenger，不等同于服务商最终送达。打开/点击继续只写专用统计表。
- 审计写入在业务处理后独立执行，失败不能回滚已完成业务；需要原子审计的事务必须使用 `internal/audit.Writer.RecordTx`，并在对应事务内补充测试。

## 请求与发送流程

- **直接导出**：客户列表导出由 `GET /api/customers/export` 直接流式返回 CSV；单客户资料和审计日志导出同样直接返回响应。`customers:export` 仅控制客户/黑名单及客户资料导出，工作区、所有权、客户列表权限和脱敏边界仍必须执行；不创建导出任务、数据库文件块或导出中心。
- **公海导出边界**：公海管理不提供独立导出或自动匹配统计；转私域由操作者填写“转入私有”原因，恢复分配后不展示旧原因。

1. `internal/auth` 验证 session、Basic/token 或 Bearer API Key，并绑定身份与 Key scope。
2. `cmd/organizations.go` 解析选定工作区；服务端重新验证组织活动状态和成员资格。
3. `cmd/workspace_permissions.go` 与 `internal/core/workspace.go` 分别应用传统功能权限和资源 `read`/`use`/`copy`/`manage` 检查。
4. 写入在事务中锁定并重新验证组织、所有权和转移状态，避免检查后状态变化造成越权。
5. 活动通过 manager 生成消息，经 messenger 投递；跟踪、退订、归档和退信由对应后台模块处理。

## 媒体文件夹不变量

- 目录名称在同一工作区、同一父目录下大小写不敏感唯一；空字符串、`.`、`..`、路径分隔符及 Windows 保留标点拒绝。根目录由 `NULL` 表示，不创建虚拟数据库行。
- 创建子目录、移动目录和移动媒体都必须验证源/目标属于同一工作区；目录移动不得把节点放入自身或自身子孙节点。组织成员资格和组织活动状态在写事务中复核。
- 删除目录不会递归删除媒体或子目录，只允许媒体数和子目录数均为零；媒体移出目录或被组织生命周期迁移时归属会置为根目录，provider 对象不受影响。
- 文件上传和列表查询的 `folder_id` 只是当前工作区内的过滤/归属字段；不带该参数保持旧的全工作区查询语义。历史媒体 URL 不因目录操作改变。

## 公海投放与回件邮箱不变量

- 最高管理员向组织划分一级公海时，在公海管理窗口选择“目标组织”。该选择只决定公海分配和联系人分配的组织归属，不切换当前工作区、不要求管理员加入组织，也不产生 `organization_members` 记录；组织统一回件邮箱由组织经理在自己的工作区设置（管理组织 -> 组织回信邮箱，`PUT /api/organizations/:id/reply-mailbox`），公海分配本身不再携带回件邮箱，普通组织用户只能操作当前组织的公海分配。
- 一级公海联系人只能从统一客户导入入口新增；导入时保存四个必需字段及安全统计，分配部门必须先在启用中的组织主数据中存在，不能把模板中的“分表1”或未知“分配部门”直接解释为组织或创建组织。公海分配绑定仍必须通过显式拆分动作完成，但导入会把合法联系人自动加入已存在的同组织公海分配；若先导入后拆分，拆分事务回填同部门联系人。最高管理员可在公海管理页为任意活跃组织完成绑定，目标组织自身的组织经理也可在该组织工作区内为自己组织完成同一拆分；组织经理不能为其它组织绑定（403），普通成员一律 403，且核心层在事务内复核目标组织活跃状态与调用者成员资格。
- 组织在公海分配手动移除联系人时，只写入 `(一级公海, 组织, 公海联系人)` 的剔除记录，不删除一级公海联系人，也不影响其他组织。该组织后续选择一级公海投放时，收件人解析必须过滤这条记录。
- 一级公海活动和公海分配活动在生成投递快照时都必须保存一级公海联系人内部 ID、目标组织、实际来源公海分配和最终回件邮箱；同一活动内按联系人内部 ID 去重。
- 活动选择公海分配或一级公海时，最终回件邮箱一律取目标组织的组织统一回件邮箱（`organizations.reply_mailbox_id`，必须 active 且已验证），公海分配不参与邮箱解析。活动配置页、预览、发送快照和回信审计均需显示“一级公海受众 -> 公海分配 -> 组织统一回件邮箱”的解析来源；活动编辑页在受众含公海时隐藏活动级回信邮箱选择并强制提交为空，也不提供任何回信配置操作。
- 客户真实邮箱只在服务端投递及回信处理链路可用；普通组织用户不得获得可复制的客户真实地址。组织统一回件邮箱是公司内部地址，组织用户和最高管理员可在活动配置、预览、发送快照及回信审计中直接查看，但最高管理员不得代为配置（该端点是组织工作区经理专属，平台管理员一律 403），也不得将其当作客户联系方式导出。
- 回复、明确退订和投诉只能剔除实际投递来源所属组织的二级分配；不能通过重新选择一级公海绕过剔除，也不能影响其他组织。
- 剔除记录必须可审计并可恢复/重新分配，但恢复与重新分配动作只能由最高管理员执行（`PUT`/`DELETE /api/org-pool-allocations/members` 及其 `/api/pools/allocations/members` 别名、`AssignPoolContact` 均由 `requirePoolAdministrator` 守卫；组织经理对这些写操作一律 403）。这与"公海分配创建/绑定可由本组织经理执行"并不矛盾：经理负责建立归属并设置本组织的统一回件邮箱，联系人主数据由最高管理员维护。恢复不能自动恢复历史活动收件人快照。
- 数据库约束每个“一级公海 × 组织”只有一个已绑定公海分配，使该组织内的联系人归属唯一可解析，收件人快照无需在多个分配之间猜测；若未来允许多个归属，必须移除此约束并要求活动显式选择公海分配。
- 一级公海活动在草稿阶段可保存，但目标组织没有有效公海分配、或没有可用的组织统一回件邮箱时，预览和发送必须阻断。该阻断不是回退到个人或系统默认邮箱：组织统一回件邮箱是目标组织显式设置的组织级配置，缺失时只能由该组织配置，诊断信息必须逐条列出缺失项并指向配置入口。
- 回件邮箱按工作区归属：个人邮箱在个人资料维护，组织邮箱在“管理组织 -> 组织回信邮箱”维护。停用只是暂停使用，不删除凭据或历史验证；重新启用时，历史验证仍在则恢复为 active，否则回到 pending 并要求重新测试。
- 组织统一回件邮箱是组织级唯一设置：只能由该组织经理为本组织指定，邮箱必须属于同一组织；平台管理员一律 403（`reply mailbox must be configured in the organization workspace`）。公海受众的回件路由只读该设置，`org_pool_allocations` 不再有回件邮箱列，活动草稿也不保存公海受众的活动级邮箱。
- 组织工作区里的回信邮箱是“共享选择、私有维护”：任何成员（包括完全没有组织管理权限的成员）都可以把本组织的任意 active 回信邮箱选进自己创建的活动，选择本身不校验所有权；邮箱的编辑、停用、重新启用与连接测试只属于其所有者，非所有者一律 404。个人工作区的回信邮箱相反：只能由本人创建、选用与维护；跨工作区或他人的个人邮箱在活动保存时返回 403。

## AI 入站回信不变量

- 只有全局 AI 设置和回信邮箱的逐邮箱开关均启用时，后台 worker 才能将该邮箱的回信正文送往 OpenAI 兼容接口；正文是非信任数据，模型只能返回固定意图，不能下达任意动作。
- Worker 必须从回信邮箱的 `organization_id`、`user_id` 约束客户匹配；地址不存在、在该边界内不唯一、成员已离组、组织已归档、自动回复、低置信度或非明确意图时，只记录审计结果而不改变客户。产品/服务类回信可记录为 `product_complaint`，同样不触发自动动作。
- 只有明确 `unsubscribe` 和明确垃圾/滥用 `complaint` 可自动执行；二者都将该工作区内的匹配客户设为 `blocklisted` 并将其全部客户列表成员关系设为 `unsubscribed`。垃圾/滥用投诉额外创建 `source=reply_ai` 的退信记录，不能伪装为邮件服务商反馈。
- 对公海投放产生的回复，处理器必须使用投递快照中的一级公海联系人、目标组织、来源公海分配和回件邮箱定位分配关系；自动处理只更新该组织公海分配的剔除状态，不得把一级公海联系人全局拉黑或从其他组织移除。
- 每封回信以邮箱与稳定消息键去重；租约、失败重试和投诉事件唯一键保证崩溃恢复不会重复拉黑或重复写入投诉。终态审计记录不保留用于模型调用的正文。
- 聚合网关下的模型可用性必须先验证后启用：设置页能取得的模型清单、连通性和分类往返结果都属于操作者可见的诊断信息，不得把「清单里存在」当成「可用于分类」；模型测试必须用真实提示词与真实端点，且探测与生产分类共用同一根地址，避免出现测试通过但生产调用失败的状态。

任何新业务流程都必须说明：所属工作区、资源所有者、可见性、可执行动作、事务边界和失败回滚行为，并补充相应测试。

## 退信邮箱只读检测（2026-09-08）

- 来源：用户确认的“读取最新一封、解析发件人/主题/退信地址、只读检测”需求。
- 检测只读取当前 POP 会话最高序号邮件，不扫描寻找退信，不保存表单、不发送邮件、不调用 DELE、不生成退信事件、不执行客户退订/拉黑。后台既有轮询不受此保证约束，仍可能独立处理邮箱；邮箱被占用时报错供重试。
- 普通邮件属于读取成功但未识别退信，空邮箱单独提示；不会把通知发件人或普通 To 字段当成失败收件人。
- DSN 各收件人块优先 Final-Recipient，再 Original-Recipient，再 X-Failed-Recipients；正文推断明确标记 body_inferred。摘要取外层邮件，日期优先 Received，缺失则以 Date 标记回退，未知不补当前时间。
- `starttls` 与 `tls_enabled` 互斥；旧配置缺失 `starttls` 时视为 false，不需要迁移。检测和保存后的后台收信使用同一连接模式。

## 角色动作细分权限（v6.38.0）

- 角色权限只决定功能动作是否可调用，不能跨越当前工作区、资源所有者、组织成员资格、归档状态、客户列表角色或个人 API Key scope。
- 客户删除、客户黑名单、客户列表归属分别由 `customers:delete`、`customers:blocklist`、`customers:membership_manage` 控制；这些动作不再由 `customers:manage` 隐式放行。所有批量/SQL 查询入口必须使用同一动作权限，并先收敛到当前用户可管理的客户集合。`customers:export` 控制客户/黑名单导出，`customers:sensitive_read` 只解除客户记录的邮箱/属性脱敏，不扩大工作区或所有权边界。
- 活动测试、排期、立即启动/恢复、暂停/取消/取消排期/归档分别由 `campaigns:test`、`campaigns:schedule`、`campaigns:send`、`campaigns:control` 控制；活动管理、所有者、SMTP、API scope 和客户列表权限仍不可省略。收件人身份明细必须有 `campaigns:recipients`、客户读取权限、个人数据追踪开关和活动隐私边界。
- 退信删除和退信客户拉黑分别由 `bounces:delete`、`bounces:blocklist` 控制；客户详情页的退信清理同样属于退信删除；选中行批量操作必须逐行通过工作区资源边界。
- 直接客户/黑名单/客户资料导出由 `customers:export` 控制；客户敏感字段由 `customers:sensitive_read` 控制。导出直接返回 HTTP 响应，不保留任务或文件，仍遵守账号、组织成员资格、归档状态、所有权、客户列表权限和脱敏边界。
- `organizations:platform_manage` 只授予平台组织管理接口；它不自动把操作者变为组织成员，也不授予客户、活动或其它资源权限。平台管理员直接创建组织时必须指定至少一名 `manager`，初始成员和批量导入成员都复用 `organization_members` 的 `member/manager` 角色；批量导入按已注册用户名/邮箱解析，任何行无效则整批不落库，且不能移除组织最后一名经理。`users:tokens` 只控制 API 用户集成令牌路由。
- `v6.36.0` 与 `v6.38.0` 为历史宽权限角色补齐对应细分权限以维持兼容；新角色的高风险细分权限默认关闭。平台管理员和用户/角色/设置/组织等平台权限不在本轮继续拆分。任何新增动作必须同步 `permissions.json`、认证常量、角色 UI 文案、服务端处理器、迁移（如需兼容）和边界测试。


## 称呼兜底

- 模板称呼规则仅修改渲染副本；不修改客户资料、真实收件人或邮件信封。
- 未启用规则保持原值；启用后空白及指定无效值使用备选称呼，其他姓名优先保留。规则不猜测真实人名。
- HTML 活动按已授权模板解析规则；可视化导入、模板/活动复制保留独立规则，旧 API 更新未传规则时不得清空。
