# 业务逻辑

## 业务权限不变量（v6.56.0）

- 五个模块呈现 20 项易懂权限名称，见 [业务权限说明](../docs/content/business-permissions.md)。不预设角色；旧角色部分授权保存不扩权。
- 功能动作与数据范围取交集；所有者和组织经理不能绕过查看、导出、统计或私域敏感权限。
- 私域删除独立于维护；没有敏感权限时列表、明细、写响应、导出和收件人/退信记录保护邮箱、UUID、属性及含身份信息的元数据，省略字段的编辑保留原值。
- 公海组织分配、主数据、投放授权互不隐含；创建普通组织分配不得新增或恢复投放授权。委派主数据维护者仍收脱敏 DTO。
- 私域与公海客户邮箱统一使用星号 `*` 打码，示例 `liuxin@gmail.com` → `liu***@gmail.com`；保留前三位前缀，剩余部分逐位替换，三位及以下的用户名全部遮罩。页面、API 与导出沿用相同格式和现有权限边界。来源：`cmd/customers.go::maskEmail`、`models/pools.go::MaskPoolEmail`。
- 全局模板也需要查看/维护权限；改变共享范围及共享目录放置另需共享权限。共享模板的私有素材关联例外不绕过素材使用权限。
- 邮箱选用与配置独立，前者不返回凭据，后者不授予活动发送。原所有者、组织管理、API Key 与归档边界继续校验。

## 核心对象

- **工作区**：个人工作区或组织工作区；请求必须先解析并验证当前用户的成员资格和组织状态。
- **组织目录**：可进入组织与实际成员组织分别维护；最高管理员可进入未加入的活跃组织，但“已加入组织”和个人资源迁移目标仍只取真实成员关系。刷新失败不能当作空列表，也不能把网络错误当作成员资格撤销；业务组件必须等启动的目录与工作区校验完成后初始化。共享目录由 `refreshOrganizationDirectory` 原子更新，并发调用共用一次请求；每次真实 API 响应及后端权限校验仍为权威。
- **客户列表与客户**：客户列表承载客户集合；普通列表默认个人私有，在组织工作区可选择组织内共享列表元数据，客户记录始终归属创建者。组织成员可查看共享列表的名称与统计，但不因此获得客户明细、导入、批量修改或发送权限；组织经理可以在当前组织检查成员资源，但不能代替所有者修改或发送。客户新建/编辑/普通导入只允许当前操作者拥有的列表，一级公海仍由独立授权路径处理。直接导出仍由 `customers:export` 控制并保持工作区、所有权和打码边界。
- **模板与活动**：模板和活动支持 `private`、`organization`、`global` 可见性；可见不等于可使用、修改或发送。
- **媒体与逻辑文件夹**：媒体二进制仍由 provider 平铺保存；`media_folders` 保存工作区目录树和个人/组织/全体权限，`media.folder_id = NULL` 表示根目录。目录内媒体按目录与全部祖先权限读取/使用，全体目录可跨工作区读取；目录改名/改权限/移动/删除需要创建者或所选工作区平台管理员及 `media:manage`。上传和嵌套创建仍限本工作区，媒体归属移动还必须由媒体所有者通过 `manage` 检查，空目录才允许删除。归档组织的共享目录不可继续公开。
- **用户与角色**：系统用户角色、客户列表角色、组织成员/经理角色和个人 API Key 是独立边界，权限只能收窄，不能扩大资源所有权。
- **一级公海与公海分配**：一级公海保存全局联系人主数据；公海分配只保存一级联系人到组织的分配关系，不复制邮箱。每个“一级公海 × 组织”只允许一个已绑定公海分配，公海分配的手动移除、回复退订和投诉均产生组织维度的逻辑剔除状态，并在一级公海中可见该组织的剔除标记。一级公海与公海分配的联系人在“客户”视图中随所选列表就地展示（仍是独立存储与安全 DTO，不伪装成普通客户），不再有单独的查看页面。
- **公海统一导入**：必填客户编号/客户编码、姓名、邮箱、分配部门，另支持可选回信邮箱 `reply_to`；其他列忽略。分配部门须匹配启用组织；非法回信地址拒绝整行，旧四列模板兼容。同身份重新导入更新回信邮箱而不增加联系人，空值清除。公海分配成员和黑名单保护沿用既有规则。
- **公海回信邮箱**：组织仍拥有唯一统一回信设置 `organizations.reply_mailbox_id`，公海分配不拥有邮箱凭据。活动配置比较“列表回信邮箱”和“组织回信邮箱”：前者仍取每条导入记录的 `reply_to`，v6.55.0 逐客户按 `pool_reply_priority` 解析，默认列表优先（`contact_first`），可选组织优先（`organization_first`）；空值回退。列表记录无地址时组织邮箱必须已验证且启用，双方均缺失则阻止发送。

## 业务审计日志

- `audit_events` 只记录低频业务操作和自动化生命周期，不替代打开、点击、收件人状态或退信事实表。稳定动作名使用英文点号命名，例如 `campaign.status_changed`、`customer.import_started`、`reply.forward_failed`、`audit.exported`。
- 每条记录必须绑定当前工作区（个人空间用 `organization_id = 0`；组织历史保留组织 ID，即使组织删除也不转成个人记录）、操作者类型、结果和对象；浏览器用户/API Key 需要保留用户与 Key ID，后台处理使用 `system`，外部退信使用 `webhook`。查询接口只能读取当前工作区。
- 审计元数据只允许稳定 ID、状态、原因码、数量和诊断摘要；低频对象可附带截断后的 `object_details` 名称/文件名/主题/状态快照，认证操作者可附带 `actor_details` 的名称/用户名。查询在 `actor_user_id` 仍存在时关联用户表展示当前用户名/名称；登录成功在会话建立前绑定用户，失败登录只保存尝试的用户名，媒体移动保存文件名及源/目标目录摘要。不得写入密码、API Key 原文、SMTP 凭据、邮件正文、附件、客户完整收件人集合或可恢复的隐私导出内容。错误原因写固定 reason code，详细错误留在运行日志。
- 活动发送器记录启动、启动失败、完成、暂停、取消和延迟；`campaign_recipients.status = sent` 的含义仍是消息交给 messenger，不等同于服务商最终送达。打开/点击继续只写专用统计表。
- 审计写入在业务处理后独立执行，失败不能回滚已完成业务；需要原子审计的事务必须使用 `internal/audit.Writer.RecordTx`，并在对应事务内补充测试。

## 请求与发送流程

- **直接导出**：客户列表导出由 `GET /api/customers/export` 直接流式返回 CSV；单客户资料和审计日志导出同样直接返回响应。`customers:export` 仅控制客户/黑名单及客户资料导出，工作区、所有权、客户列表权限和脱敏边界仍必须执行；不创建导出任务、数据库文件块或导出中心。
- **公海导出边界**：公海管理不提供独立导出或自动匹配统计；转私域由操作者填写“转入私有”原因，恢复分配后不展示旧原因。

1. `internal/auth` 验证 session、Basic/token 或 Bearer API Key，并绑定身份与 Key scope。
2. `cmd/organizations.go` 解析选定工作区；服务端重新验证组织活动状态和成员资格。
3. `cmd/workspace_permissions.go` 与 `internal/core/workspace.go` 分别应用传统功能权限和资源 `read`/`use`/`copy`/`manage` 检查。
4. 写入在事务中锁定并重新验证组织、所有权和转移状态，避免检查后状态变化造成越权。
5. 活动通过 manager 生成消息，经 messenger 投递；跟踪、退订、归档和退信由对应后台模块处理。

## 媒体文件夹不变量

- 目录名称在同一工作区、同一父目录下大小写不敏感唯一；空字符串、`.`、`..`、路径分隔符及 Windows 保留标点拒绝。根目录由 `NULL` 表示，不创建虚拟数据库行。
- 创建子目录、移动目录和移动媒体都必须验证源/目标属于同一工作区；目录移动不得把节点放入自身或自身子孙节点。组织成员资格和组织活动状态在写事务中复核。
- 删除目录不会递归删除媒体或子目录，只允许媒体数和子目录数均为零；媒体移出目录或被组织生命周期迁移时归属会置为根目录，provider 对象不受影响。用户物理删除时只清理该用户的个人目录，组织目录保留并清空创建者引用，目录内媒体同样回到根目录。
- 文件上传的 `folder_id` 只能指向当前工作区可读目录；列表查询可浏览全体共享目录。不带该参数返回可读媒体（包含全体共享目录），根目录媒体仍受旧的工作区资源边界约束。目录内媒体直接 URL 不得绕过祖先权限；URL 文本不因目录操作改变。

## 公海投放与回件邮箱不变量

- 最高管理员向组织划分一级公海时，在公海管理窗口选择“目标组织”。该选择只决定公海分配和联系人分配的组织归属，不切换当前工作区、不要求管理员加入组织，也不产生 `organization_members` 记录；组织统一回件邮箱由组织经理在自己的工作区设置，或由具备 `organizations:platform_manage` 的平台组织操作员在管理组织页面选定目标组织后设置（管理组织 -> 组织回信邮箱，`PUT /api/organizations/:id/reply-mailbox`），公海分配本身不再携带回件邮箱，普通组织用户只能操作当前组织的公海分配。
- 公海主数据新增与导入需 `pools:master_manage`；分配部门必须匹配启用组织，不自动创建组织。合法联系人加入已有同组织分配，后建分配回填同部门联系人。创建分配需 `pools:manage`，普通成员在当前组织且已有投放授权，跨组织目标还需 `pools:delivery_manage`。Core 锁定组织并重验状态、成员与授权。
- 公海客户汇总按“一级公海 × 联系人”展示；同一联系人属于多个公海时保留多行和各自的所属列表、移除状态，不跨公海去重。搜索、计数、分页与导出必须使用同一工作区可见范围。组织用户只能读本组织分配成员且邮箱脱敏；平台管理员可跨公海查看完整记录。
- 仪表盘的私域客户、公海客户和公海列表分别统计：`private_customers` 沿用当前工作区普通客户的所有者边界，`pool_customers` 按“一级公海 × 联系人”成员行统计总数、正常和已移除，`pool_lists.total` 只统计启用的一级公海列表，不把组织公海分配当作独立列表；平台管理员看全局，组织用户只看本组织分配及已授权列表，个人空间两项公海统计均为零。`customers` 字段作为旧客户端的私域兼容别名。
- 公海列表明细中的已绑定/未绑定之和等于一级公海总数；仅启用公海、启用分配列表和启用组织组成有效绑定，未关联一级公海的分配不计入。绑定组织数去重；普通组织工作区的绑定、分配和组织数只计算本组织，即使同一公海另有其它组织绑定也不跨界统计。来源：`internal/core/dashboard.go`、`internal/core/dashboard_counts_db_test.go`。
- 邮件打开地图的城市汇总按国家、地区、城市三者分组，同名异地城市不合并；没有城市名的定位行保持未知，不能用地区或国家冒充城市。国家切换和城市聚焦只展示当前活动报告接口已授权的聚合；空数据或失败清除旧热点并保留底图和国家选择。来源：`frontend/src/{components/CampaignGeoHeatmap.vue,utils/campaignGeo.js}`、`frontend/cypress/e2e/campaign-geo.cy.js`。
- 组织在公海分配手动移除联系人时，只写入 `(一级公海, 组织, 公海联系人)` 的剔除记录，不删除一级公海联系人，也不影响其他组织。该组织后续选择一级公海投放时，收件人解析必须过滤这条记录。客户视图的一级公海「已移除客户」汇总各组织尚未恢复的移除/剔除记录，按联系人 ID 去重；组织视图只看本组织。无分配的联系人仍在「公海客户」中，恢复分配后重新回到该栏。
- 一级公海活动和公海分配活动在生成投递快照时都必须保存一级公海联系人内部 ID、目标组织、实际来源公海分配和最终回件邮箱；同一活动内按联系人内部 ID 去重。
- 公海邮件中的打开像素和追踪链接使用该投递快照对应的公海联系人 UUID；公开端点只为活动内有效收件人记录个体事件，点击还需活动与目标链接关联。打开与点击按公海联系人 ID 计数，发送分母按实际成功投递时间计数；未启用个体追踪时只记录活动级事件。公海收件人明细受 `pools:get` 和本组织边界约束，非最高管理员的邮箱必须脱敏、UUID 不得回传。
- 活动选择一级公海时，逐客户使用客户/组织优先级中的第一个可用地址。配置页显示顺序，快照保存实际地址和来源，发送以快照为准；公海受众活动级回信邮箱仍为空，活动可调整两个公海来源的顺序。
- 客户真实邮箱只在服务端投递及回信处理链路可用；普通组织用户不得获得可复制的客户真实地址。组织统一回件邮箱是公司内部地址，组织用户和最高管理员可在活动配置、预览、发送快照及回信审计中直接查看；组织经理和具备 `organizations:platform_manage` 的平台组织操作员可在管理组织页面为选定组织配置，也不得将其当作客户联系方式导出。
- 回复、明确退订和投诉只能剔除实际投递来源所属组织的二级分配；不能通过重新选择一级公海绕过剔除，也不能影响其他组织。
- 剔除记录必须可审计并可恢复。恢复、重新分配、移除需 `pools:manage`，普通调用者限本组织分配。清邮属于主数据维护，需 `pools:master_manage`。查看与导出分别需 `pools:get`、`pools:export`；创建本组织分配先检查已有授权，只有投放授权管理者可授予/撤销授权。恢复不自动恢复历史活动快照。
- 数据库约束每个“一级公海 × 组织”只有一个已绑定公海分配，使该组织内的联系人归属唯一可解析，收件人快照无需在多个分配之间猜测；若未来允许多个归属，必须移除此约束并要求活动显式选择公海分配。
- 一级公海活动在草稿阶段可保存；目标组织没有有效公海分配，或有效客户既无导入回信地址也无可用组织回退地址时，预览和发送阻断。空分配保留组织邮箱配置检查。诊断逐条列出缺失项；配置组织回退或补全客户地址可解决回信路由缺口。
- 回件邮箱按工作区归属：个人邮箱在个人资料维护，组织邮箱在“管理组织 -> 组织回信邮箱”维护。停用只是暂停使用，不删除凭据或历史验证；重新启用时，历史验证仍在则恢复为 active，否则回到 pending 并要求重新测试。
- 组织统一回件邮箱由该组织经理或有平台管理权限的操作员维护，邮箱须属于同一组织。它是公海路由的组织来源，不覆盖默认客户优先选择；`org_pool_allocations` 不持有邮箱凭据。导入回信地址不自动开通收信，实际地址仅匹配同组织 active/已验证邮箱时关联收信 ID。
- 组织回信邮箱可共享选用，维护仍归所有者：选用本组织 active 邮箱需 `mailboxes:use`，不要求邮箱所有权；编辑、测试与启停需 `mailboxes:manage` 且为所有者，组织经理可按既有清理规则删除遗留邮箱。个人邮箱仅本人选用与维护，跨工作区或他人个人邮箱拒绝。配置权限不包含活动发送。

## 平台级公海营销不变量（全量组织 + 组织 SMTP 池轮询）

- **SMTP 配置归属**：平台只保留一个用于系统通知的 SMTP；活动使用账号或组织 SMTP 池，事务邮件使用账号池。连接数、重试、超时、随机延迟、邮件头统一取 `settings.smtp_delivery`，对各 SMTP 分别应用；主机、认证、TLS、From 与每日额度取各 SMTP 自身配置。v6.53.0 将旧全局 TLS 生效值迁入各行，保留凭据和 UUID。
- **随机投递延迟**：`smtp_delivery.send_delay_min/max` 为整数毫秒，范围 `0 ≤ 下限 ≤ 上限 ≤ 3600000`，两者为 0 时关闭；旧时长字符串兼容读取并按原时长升级。每封邮件抽取均匀整数毫秒等待，同一进程同 SMTP UUID 跨缓存池共用并发容量与延迟队列；开启延迟时依次等待并发送，不同 SMTP 独立。暂停/取消和关闭中断等待、释放每日额度预占；连接测试跳过随机等待，网络重试不重新抽样。来源：`models/settings.go`、`internal/messenger/email/send_delay.go`、`internal/manager/{manager,pipe}.go`。
- **三级投递限制**：活动 `smtp_rate_limit` 为所有发件 SMTP 的合计封/分钟，1–1000000，个人来源默认 20、组织来源默认 100；活动 UUID 共用平滑发送间隔。平台 `app.message_rate` 与滑动窗口为所有 SMTP 合计硬上限，`app.concurrency` 限制实际总投递并发，工作线程数不放大发送频率；各 SMTP 再受统一投递参数独立限制。达到任一上限就等待，等待不算投递错误或已发送；系统通知与连接测试也受平台总限速。完成或失败释放平台并发许可，暂停/关闭中断排队。状态仅在单进程内共享，重启重置。来源：`internal/messenger/email/delivery_limiter.go`、`internal/manager/manager.go`、`cmd/send_limits.go`、`internal/migrations/v6.53.0.go`。

- **受众范围**：`campaigns.pool_scope = 'all_organizations'` 的活动只能选择一级公海列表（不接受显式公海分配列表、不允许混入普通客户列表），受众为该一级公海下所有活跃组织的公海分配并集。该能力由专用权限 `campaigns:public_pool_send` 控制；没有该权限的请求一律按单组织范围（`organization`）处理或直接 403。
- **去重与归属**：同一公海联系人属于多个组织时，本活动只发送一次，归属为活动持久化组织顺序中的第一个组织；该邮件的发件 SMTP 池与 Reply-To 都取该组织。投递历史行（`queued`/`sent`/`cancelled`）的目标组织、回件邮箱与发件人不因后续重排或配置变更被改写，只有 `pending`/`deferred` 行参与刷新。
- **组织顺序**：组织顺序在活动首次可发送时随机生成并写入 `campaign_pool_org_orders`，此后不重排；暂停、服务重启、次日续发都沿用同一顺序。`campaigns.pool_next_org_index` 记录轮转位置，使并发批次与恢复后的活动继续轮转而不是每次从头开始。组织不再拥有该公海的活跃分配时，其顺序行被清理。
- **组织 SMTP 池**：每个组织的池由“组织活跃 + 成员未离组 + 用户 enabled + SMTP enabled”动态过滤后的所有 SMTP 行扁平组成，排序稳定为（user_id, smtp id）。发件人在每次领取收件人时重新分配，因此成员离组、账号停用、SMTP 停用立即生效，新增 SMTP 立即参与后续轮询。
- **持久化轮询游标**：组织级游标 `org_pool_smtp_cursors.next_smtp_uuid` 在该组织的所有公海活动之间共享，并在数据库行锁（`FOR UPDATE`）下推进；多个 worker 或多实例并发领取时不会重复或跳号。游标只保存稳定 UUID，成员增删不影响其含义。
- **额度**：不新增平台级或组织级固定总额度。每个活动仍受 `daily_send_limit` 限制，每个 SMTP 行仍受自身 `daily_limit` 限制，且该额度在所有使用它的公海活动之间共享。额度预检（组织聚合剩余）只用于决定批量大小，最终上限由发送时的原子额度预占（`smtpQuotaTracker.ReserveServer`）保证。
- **失败语义**：某 SMTP 额度耗尽时跳过并继续使用同组织其他可用 SMTP；某组织全部 SMTP 额度耗尽时该组织本轮不领取收件人，全部组织均耗尽则按 `daily_resume_time` 延迟。某一组织**没有任何**可用 SMTP 时（结构性缺失）整个活动暂停并提示修复，不回退活动所有者或平台 SMTP。发送结果不确定（超时/连接中断）时，重试保持原发件人分配，不跨账号重发，以免同一客户重复收到邮件；系统整体仍为 at-least-once。
- **启动阻断**：预览/发送前校验每个目标组织：组织活跃、每个有效客户有回信地址或 active 且已验证的组织回退、所选 SMTP 来源有可用账号；任一组织不满足即阻止整个活动，错误逐条列出组织与缺失项。空分配保留组织邮箱配置检查；全组织活动运行中变为不满足时暂停并提示修复。
- **权限与凭据**：成员 SMTP 凭据只在服务端投递链路使用；任何 API、前端或审计输出都不得返回其他成员的主机、用户名或密码，`GET /api/campaigns/:id/pool-send-status` 只返回组织名、回件邮箱地址与 SMTP 数量。持有 `campaigns:public_pool_send` 的账号可以启动/排期他人创建的全量公海活动，但该权限不扩大普通活动、客户明细或组织管理能力。
- **回件路由**：平台级公海邮件 From 取分配的 SMTP；Reply-To 取逐客户按活动优先级解析的 `reply_to_snapshot`。客户地址为空时回退组织地址，组织来源不可用时可回退客户地址；无可用地址阻止发送。排队/成功/取消的历史路由不重写。

## AI 入站回信不变量

- 只有全局 AI 设置和回信邮箱的逐邮箱开关均启用时，后台 worker 才能将该邮箱的回信正文送往 OpenAI 兼容接口；正文是非信任数据，模型只能返回固定意图，不能下达任意动作。
- Worker 必须从回信邮箱的 `organization_id`、`user_id` 约束客户匹配；地址不存在、在该边界内不唯一、成员已离组、组织已归档、自动回复、低置信度或非明确意图时，只记录审计结果而不改变客户。产品/服务类回信可记录为 `product_complaint`，同样不触发自动动作。
- 只有明确 `unsubscribe` 和明确垃圾/滥用 `complaint` 可自动执行；二者都将该工作区内的匹配客户设为 `blocklisted` 并将其全部客户列表成员关系设为 `unsubscribed`。垃圾/滥用投诉额外创建 `source=reply_ai` 的退信记录，不能伪装为邮件服务商反馈。
- 对公海投放产生的回复，处理器必须使用投递快照中的一级公海联系人、目标组织、来源公海分配和回件邮箱定位分配关系；自动处理只更新该组织公海分配的剔除状态，不得把一级公海联系人全局拉黑或从其他组织移除。
- 每封回信以邮箱与稳定消息键去重；租约、失败重试和投诉事件唯一键保证崩溃恢复不会重复拉黑或重复写入投诉。终态审计记录不保留用于模型调用的正文。
- 聚合网关下的模型可用性必须先验证后启用：设置页能取得的模型清单、连通性和分类往返结果都属于操作者可见的诊断信息，不得把「清单里存在」当成「可用于分类」；模型测试必须用真实提示词与真实端点，且探测与生产分类共用同一根地址，避免出现测试通过但生产调用失败的状态。

任何新业务流程都必须说明：所属工作区、资源所有者、可见性、可执行动作、事务边界和失败回滚行为，并补充相应测试。

## 退信邮箱只读检测（2026-09-08）

- 来源：用户确认的“读取最新一封、解析发件人/主题/退信地址、只读检测”需求。
- 检测只读取当前 POP 会话最高序号邮件，不扫描寻找退信，不保存表单、不发送邮件、不调用 DELE、不生成退信事件、不执行客户退订/拉黑。后台既有轮询不受此保证约束，仍可能独立处理邮箱；邮箱被占用时报错供重试。
- 普通邮件属于读取成功但未识别退信，空邮箱单独提示；不会把通知发件人或普通 To 字段当成失败收件人。
- DSN 各收件人块优先 Final-Recipient，再 Original-Recipient，再 X-Failed-Recipients；正文推断明确标记 body_inferred。摘要取外层邮件，日期优先 Received，缺失则以 Date 标记回退，未知不补当前时间。
- `starttls` 与 `tls_enabled` 互斥；旧配置缺失 `starttls` 时视为 false，不需要迁移。检测和保存后的后台收信使用同一连接模式。

## 角色动作细分权限（v6.38.0）

- 角色权限只决定功能动作是否可调用，不能跨越当前工作区、资源所有者、组织成员资格、归档状态、客户列表角色或个人 API Key scope。
- 客户删除、客户黑名单、客户列表归属分别由 `customers:delete`、`customers:blocklist`、`customers:membership_manage` 控制；这些动作不再由 `customers:manage` 隐式放行。所有批量/SQL 查询入口必须使用同一动作权限，并先收敛到当前用户可管理的客户集合。`customers:export` 控制客户/黑名单导出，`customers:sensitive_read` 只解除客户记录的邮箱/属性脱敏，不扩大工作区或所有权边界。
- 活动测试、排期、立即启动/恢复、暂停/取消/取消排期/归档分别由 `campaigns:test`、`campaigns:schedule`、`campaigns:send`、`campaigns:control` 控制；活动管理、所有者、SMTP、API scope 和客户列表权限仍不可省略。收件人身份明细必须有 `campaigns:recipients`、客户读取权限、个人数据追踪开关和活动隐私边界。
- 退信删除和退信客户拉黑分别由 `bounces:delete`、`bounces:blocklist` 控制；客户详情页的退信清理同样属于退信删除；选中行批量操作必须逐行通过工作区资源边界。
- 直接客户/黑名单/客户资料导出由 `customers:export` 控制；客户敏感字段由 `customers:sensitive_read` 控制。导出直接返回 HTTP 响应，不保留任务或文件，仍遵守账号、组织成员资格、归档状态、所有权、客户列表权限和脱敏边界。
- `organizations:platform_manage` 只授予平台组织管理接口；它不自动把操作者变为组织成员，也不授予客户、活动或其它资源权限。平台管理员直接创建组织时必须指定至少一名 `manager`，初始成员和批量导入成员都复用 `organization_members` 的 `member/manager` 角色；批量导入按已注册用户名/邮箱解析，任何行无效则整批不落库，且不能移除组织最后一名经理。`users:tokens` 只控制 API 用户集成令牌路由。
- `v6.36.0` 与 `v6.38.0` 为历史宽权限角色补齐对应细分权限以维持兼容；新角色的高风险细分权限默认关闭。平台管理员和用户/角色/设置/组织等平台权限不在本轮继续拆分。任何新增动作必须同步 `permissions.json`、认证常量、角色 UI 文案、服务端处理器、迁移（如需兼容）和边界测试。


## 称呼兜底

- 模板称呼规则仅修改渲染副本；不修改客户资料、真实收件人或邮件信封。
- 未启用规则保持原值；启用后空白及指定无效值使用备选称呼，其他姓名优先保留。规则不猜测真实人名。
- HTML 活动按已授权模板解析规则；可视化导入、模板/活动复制保留独立规则，旧 API 更新未传规则时不得清空。
- 来源：`models/name_fallback.go`、`internal/manager/message.go`、`internal/core/workspace_actions.go`、`internal/core/templates.go`。

## 独立组织营销 SMTP

- `user_smtp_servers.user_id` / `organization_id` 必须且只能存在一个，组织 SMTP 不是成员个人 SMTP 的汇总；使用量按独立 UUID 记录，不跨 owner。
- 每个组织可拥有多个 `organization_smtp_pools`；SMTP 行和组织来源活动必须引用同组织的 `smtp_pool_id`。池删除前必须为空且无活动引用，旧组织行由 v6.52.0 迁移到默认发件池；活动概览、额度与实际投递只使用所选池。
- 组织经理/平台组织操作员可编辑、删除和测试，普通成员仅通过活动权限读取安全发件概览；跨组织/个人 SMTP ID 不能替换、删除或借用密码。
- `campaigns.smtp_source` 默认 personal，organization 来源只用于所属组织或全组织公海目标组织；没有 SMTP 不回退，配额耗尽延迟。系统通知和事务邮件所有权不变。两种来源都应用统一投递和随机延迟。
- 已有活动概览取活动 owner/组织，不取查看者；概览永不读取密码/用户名/主机字段。全组织公海准备状态、分配器、额度查询和概览遵循同一个来源。
- 实现：`cmd/organization_smtp.go`、`cmd/personal_smtp.go`（可信正/负 owner key）、`cmd/manager_store.go`、`internal/manager/manager.go`、`queries/misc.sql`、`queries/campaigns.sql`、`internal/migrations/v6.50.0.go`。
