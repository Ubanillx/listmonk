# Delivery provider reporting API

All GET `/api/delivery-provider/*` routes (including safe configuration status, account details, reports, logs and Excel export) require the explicit **`delivery_provider:get`** permission; built-in platform administrators retain access. PUT `/config` and POST `/test` remain restricted to platform administrators: the read grant cannot change credentials or trigger connection tests. Missing permission returns HTTP 403 before loading credentials or contacting the provider. Organization ownership, workspace selection, mailbox administration and ordinary settings permissions do not grant access. Personal API keys are outside the independent route allowlist. Responses use the existing `{ "data": ... }` envelope and `Cache-Control: no-store`.

| Method | Route | Contract |
| --- | --- | --- |
| GET | `/api/delivery-provider/config` | Safe status only: `username`, `configured`, `has_password`, `updated_at`, `tested_at`, `test_error`, `verified`, `provider`. Never returns a password. |
| PUT | `/api/delivery-provider/config` | JSON `username`, `password`, `expected_updated_at`. Empty password keeps the previous one only for the same username. New configuration uses empty `expected_updated_at`. Stale versions return 409. No external request during save. |
| POST | `/api/delivery-provider/test` | Uses saved credentials to query customer and service. Persists safe success/failure metadata. Returns status including `verified`; a provider connection failure is represented by `verified: false`, `test_error`, with HTTP 200 after successfully persisting the result. Infrastructure errors remain non-200. |
| GET | `/api/delivery-provider/account` | `results: { customer, service }`, `source`, `fetched_at`, `warning`. Service failure can return account details with a warning and missing service. |
| GET | `/api/delivery-provider/statistics` | `date`, `date_end` in YYYY-MM-DD, and/or `ident` or positive sending task `id`; omit dates for full-task results. At least a date or task is required. |
| GET | `/api/delivery-provider/failures` | At least one of `date`, `date_end`, `task_ident`, `task_id`; required numeric-string `type` in -1,1..10. Without a task selector, the backend requests `type=-1` for the date range and filters the requested type locally before grouping/export; types 1..3 do not require a batch in this API. With a task selector, the requested type is forwarded unchanged. Optional `search` performs local case-insensitive email substring filtering. Optional `group_by=email` merges repeated addresses and counts occurrences. Neither local option is forwarded to BestEDM. |
| GET | `/api/delivery-provider/failures/export` | Same applied filters including `search` and `group_by=email`; optional `lang`; returns `.xlsx`, including source column and, when grouped, a numeric error count and all classifications/descriptions with their counts. |
| PUT | `/api/delivery-provider/failures/blocklist` | JSON `emails` (array; `email` is accepted for a single address), `action` (`block` or `unblock`) and `scope` (`all`, `private` or `pool`). At most 500 addresses per request. Requires `delivery_provider:get` and `delivery_provider:blocklist`. Re-resolves each address server-side, applies only targets inside `scope` that the caller may change, and returns `applied` (with `email`, `kind`, `id`), `skipped` (with `email` and `reason`) and `unmatched` (array of addresses). Unmatched addresses are skipped and never create customers. |
| GET | `/api/delivery-provider/logs` | Required `date`, full `mail_to`; optional `task_ident`. The UI can issue one user-triggered request from a failed address, using the earliest loaded statistic date in the selected batch (or all loaded statistics without a batch). Missing statistic dates fall back to the applied range start. No automatic polling or cross-date retries. |

Report routes return `data: { results: [...], source: "live", fetched_at, warning }`. Field keys inside raw report records retain the provider's snake_case/compound keys. Missing numerical fields are not synthesized. Without `group_by=email`, repeated failed addresses remain separate records for compatibility. `task_id` in a statistics record is not the sending task ID.

With `group_by=email`, each failure result has `email`, numeric `error_count`, `errors: [{error_type, error_type_dec, error_count}]`, and `matches: [{kind, id, pool_id, pool_name, customer_code, name, status, blocked, can_block}]` for the current workspace. Matching is case-insensitive and exact after trimming; private matches follow the owner boundary, pool matches follow platform/pool-master scope or the organization's active allocation memberships. A match never includes an e-mail address, and a failing match lookup only omits `matches` from the response. Email grouping trims whitespace and ignores case, retaining the first spelling and first-seen order. Every distinct classification/description is preserved. Counts refer to occurrences in the filtered upstream response, not inferred SMTP attempts or unique sends. Filtering happens before aggregation; the console paginates these email groups. Empty results remain `[]`. The export uses the same aggregation function. Other nonempty `group_by` values are rejected.

There is no sample mode: `mode` is not an accepted query field, so `mode=demo` and similar requests fail validation with HTTP 400. Every report route reads the saved credentials and reports upstream failures as errors rather than empty or zeroed results. Configuration and test endpoints always concern the real account.

An empty result is successful: the provider answers "no rows" with `{"err_msg": "未找到相应结果…"}` on the log API and `<result><status>no_data</status></result>` on the report APIs. Both become `results: []` with HTTP 200, so the console shows an empty table. Other `err_msg` texts and non-`no_data` statuses remain errors.

Queries reject unknown/repeated fields (including `mode`), invalid dates, reversed ranges, non-positive IDs, invalid emails, ambiguous ID+batch selectors and date ranges over 366 days. Reports limit each provider response to 4 MB. Errors use the normal Listmonk HTTP error envelope, with safe descriptions and provider error codes; raw response bodies and credentials are not logged or returned.

Failure XML alone tolerates bare ampersands in plain-text `<email>` elements: they are escaped before strict XML parsing, preserving the decoded email, duplicate records, classifications and descriptions. Existing XML entities, CDATA, comments, processing instructions and attributes are left untouched. Other malformed XML still fails the entire query; records are never silently skipped. This compatibility applies equally to raw failures, email grouping and Excel export, and does not relax account, statistics or log parsing.

Account settings are kept in the reserved `settings` row `integration.bestedm`; ordinary settings models omit that key and the generic keyed write endpoint rejects it. Save uses a transaction/advisory lock and version check. Test-result writes compare the original JSON record so stale in-flight tests cannot overwrite a newly saved credential pair. The connection does not reload the app or modify SMTP transports.

## Platform automatic blocklisting

All automation routes require a platform administrator, including GETs; report and manual blocklist permissions do not grant access. Responses retain snake_case and `Cache-Control: no-store`. Organization headers do not alter the fixed platform scope.

| Method | Route | Contract |
| --- | --- | --- |
| GET | `/api/delivery-provider/automation` | `data: {timezone, scopes: [{rule, runs}]}`. Exactly `private` and `pool`, each with `version`, `config`, `next_run_at`, `last_run_at`; latest 20 runs per scope. |
| PUT | `/api/delivery-provider/automation/:scope` | `{version, config, preview_id}`. Version conflict or busy worker returns 409. Enabling requires a successful preview of the same scope, version and normalized config within 15 minutes; disabling does not. Returns saved rule with incremented version. |
| POST | `/api/delivery-provider/automation/:scope/preview` | `{version, config}`. Read-only matching; persists preview evidence and returns `data: {run, items}` (first 50). No customer changes. |
| POST | `/api/delivery-provider/automation/:scope/run` | `{version, preview_id, config?}`. Requires a fresh successful preview for the same scope, current rule version and normalized config. With `config`, applies these manual conditions without saving the rule or changing its version, enabled state, last/next scheduled timestamps. Without `config`, retains the saved-rule behavior (including rescheduling). Rechecks targets and applies once; scheduling may remain disabled. Returns `data: {run, items}`. |
| GET | `/api/delivery-provider/automation/:scope/runs/:id?page=1` | Paginated details array (50 per page), scoped to the requested rule. |

The admin UI automatically checks before schedule saves and before a manual confirmation; users do not manage preview IDs. Canceling a manual confirmation performs no rule/customer write, although its read-only check is retained in history. The optional manual config does not grant any additional role or workspace access.

Config: `{enabled: boolean, types: [1..10], schedule: "daily"|"interval", daily_time: "HH:MM", interval_hours: 1..168, lookback_days: 1..31, excluded_emails: [...]}`. Types must be nonempty/unique, exclusions at most 1000 addresses; exclusion matching uses trimmed lowercase without guessing malformed addresses. Daily time and interval hours must both be valid even when inactive. Defaults: disabled, types `[1,3,6,8,9]`, daily 02:00, interval 24, lookback 7, exclusions []; clock uses deployment timezone.

Run fields: `id`, `scope`, `version`, `trigger` (`preview|manual|scheduled`), `status` (`running|preview|success|failed|interrupted`), `date_start`, `date_end`, `counts`, safe `error`, `created_at`, `finished_at`. Counts: `addresses` (selected unique emails), `to_block` (eligible target records newly blocked on success), `already`, `excluded` (emails), `unmatched` (emails), `skipped` (ineligible targets). Details: `target_id` (0 when unmatched/excluded), `email`, `name`, `evidence: {email, types, count}` (returned occurrences, never SMTP attempts), `outcome` (`to_block|blocked|already|excluded|unmatched|skipped`). Private and pool counts are independent for identical emails.

Private rules cover all existing personal/organization customers and unsubscribe list memberships when blocklisting; pool rules change shared contacts across organizations. Transfers, archived organizations and archived pool contacts are skipped. No record creation, automatic unblocking or re-subscription. Exclusions protect manually restored customers. Runs fetch a date-scoped all-types report with the adapter's XML compatibility/4 MB bound and filter locally; no per-batch fanout. Target mutations and details commit atomically. Error responses never expose DB statements, raw provider data or credentials; failed/interrupted runs remain visible. History remains in PostgreSQL without automatic pruning.
