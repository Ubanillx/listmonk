# 回信自动检测与处理层级（2026-11-05）

用户任务：为自己的回信邮箱选择是否自动检测，并决定使用 AI 处理客户回信、自动处理退信，或同时使用两项。

用户已明确结构，直接实施一个方向：回信地址 → 自动检测总开关 → 检测后的处理方式（AI / 退信）→ 共用收件连接 → 保存/测试。原页面两个并列处理开关控制连接区显示，无法单独暂停自动化，容易误以为必须选择处理功能才能配置连接。

## 工作系统契约

- 对象为个人/组织回信邮箱，入口保持个人邮件配置和组织邮箱配置，共用 `ReplyMailboxSettings.vue`；不更换导航、品牌和组件。
- 沿用现有 Buefy 开关、表单和按钮，以及 `--lm-*` 变量。总开关放在回信地址下；开启后下层区域以浅中性背景表达从属关系，内部两项处理方式桌面并列、手机纵排，收件连接只配置一次。
- `scan_enabled` 独立保存；关闭后连接与 AI/退信选择保留，不再检测或提交处理副作用。生命周期的停用/保留状态仍独立生效。
- 可先开启总开关、保存并测试连接，再启用任一处理方式；两项均未选择时提示尚未启用处理，不假装正在处理。全局 AI / 退信服务条件继续有效。
- 主动作保持保存，测试要求已保存的连接。失败保留输入；密码只在服务端保存。切换只改变本邮箱的草稿，显示待保存状态。
- 状态覆盖：地址模式、检测开启但尚无处理、AI 单开、退信单开、双开、暂停后刷新/恢复、保存和连接失败、只读邮箱。
- 动效沿用开关自带反馈与按钮加载，展开直接呈现，不添加装饰动画；键盘和减少动态设置下功能完整。

计数口径：从已保存邮箱卡片开始，不计文字输入与页面入口。原先暂停两项已启用处理需关两个开关再保存（3 次），现在关闭总开关再保存（2 次），恢复时保留原选择。首次启用退信由原 4 次（开退信、确认、保存、测试）变为 5 次（增加明确的检测总开关）；改善在于父子关系和防错，不宣称首次设置步骤减少。基线来自用户当前页面截图及原有浏览器回归。

## 取消确认修正（2026-11-06）

用户反馈退信确认框“取消”无法关闭，新增 `reply-mailbox-confirmation.cy.js` 先实际点击复现：弹窗始终存在。`Utils.confirm` 将第三参 `null` 透传为 Buefy 的 `onCancel`，覆盖组件默认函数，`cancel()` 调用 `.apply()` 时异常，后续关闭无法执行。共享封装将非函数取消回调归一为缺省值，真实回调保持原样。

第一步修正后，弹窗已关闭，但回归断言又发现退信开关外观仍开启：原来单向 `value` 绑定未更新 Buefy 内部状态。改为草稿双向绑定，并在三个确认分支的取消回调中恢复关闭；按钮、Esc 均使用同一取消行为。回归同时检查桌面/手机取消后弹窗消失、退信开关关闭、仍无处理方式，再次开启并确认成功，以及共享封装对 `null`、省略回调和真实回调的兼容性。

最终执行 `node dev/run-cypress.js --spec cypress/e2e/reply-mailbox-confirmation.cy.js,cypress/e2e/reply-mailbox-config.cy.js`，两组共 8/8 通过、0 失败。前端 lint 只有既有地图 shadow warning，生产构建通过；本地 backend 已重启，9173 HTTP 200，启动无新增错误且无待升级。已核对[取消后的真实截图](shots/reply-mailbox-cancelled.png)，弹窗消失、两处理开关关闭。未连接真实邮箱或发送邮件。
